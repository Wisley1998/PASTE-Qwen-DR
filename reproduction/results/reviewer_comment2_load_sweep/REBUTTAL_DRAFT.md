# Proposed response to common comment 2

We thank the reviewers for identifying an ambiguity in how we reported prediction quality and realized speculation effectiveness. The previously juxtaposed numbers did not share a numerator, denominator, or even an evaluation scope. We have corrected the terminology and will report every value as a count as well as a percentage.

In particular, the 93.8% value in the current code is **event coverage at prefetch width N=4**, not the fraction of speculative executions that hit. The same source reports a per-prefetch hit rate of 67.8% at N=4. Moreover, the exact 27.8% and 43.9% prediction values cannot be regenerated from the checked-in artifacts. The closest reproducible measurements are 8/28=28.6% Top-1 on Gemini CLI's safe-target *tool-name* diagnostic and 38/88=43.2% Top-3 on Qwen-DR's exact held-out URL invocations. These are different workloads and must not be combined. We will therefore remove the ambiguous aggregate claim and replace it with a per-workload table that states the prediction object, numerator, denominator, candidate budget, and whether the value is name-level, exact-invocation, selected before admission, admitted, or committed.

For Qwen-DR, 34 denotes search-to-visit decision windows, while batched visits expand to 88 atomic authoritative URL invocations; decision hit rate therefore uses 34 and exact target recall uses 88. For Gemini CLI, the ranker emits tool names at all 81 held-out next-tool windows, but only 28 targets are safe-local. Safe-target recall uses 28, whereas unthrottled selected-prediction precision counts the name predictions from all 81 windows. Those Gemini predictions have no executable arguments: the all-target name diagnostic (39/81 Top-1 and 71/81 Top-3), safe-target name diagnostic (8/28 and 24/28), and causal exact-match opportunities (2/28) are distinct measurements.

To directly address effectiveness under throttling, we added a load-by-budget replay over Qwen-DR's whole-session held-out set (34 search-to-visit decisions and 88 authoritative URL invocations). This is our lowest exact-invocation predictability workload: Top-1 is 17/88=19.3%, Top-3 is 38/88=43.2%, and Top-5 is 49/88=55.7%. With all requested candidates admitted, budgets 1/3/5 reduce trace-derived exposed tool stall by 23.5%/42.1%/49.0%. When only 50% of requested speculative candidates can be admitted after authoritative work, realized target coverage is 9.9%/27.3%/39.3% and stall reduction is 12.1%/30.3%/39.7%. Under a severe 10% admission envelope, coverage is 1.7%/5.8%/9.9% and stall reduction is 2.0%/7.3%/12.1%. At saturation, no speculative candidates are admitted, both extra work and speculative benefit become zero, and execution falls back to the authoritative path.

We additionally exercised the repository's bounded exact-confirmation scheduler with the same held-out labels, budgets 1/3/5, 1/8/32 concurrent opportunities, and a fixed eight-slot speculative cap. Capacity rejection rises as expected, while all nine cells show zero speculative-state commits before exact authoritative confirmation. At high concurrency the wider candidate budget no longer increases realized coverage because the same fixed slots admit only the highest-ranked candidates. We use synthetic 5 ms service only to trigger admission pressure, so this component test is evidence about admission/fallback correctness rather than an end-to-end GPU performance claim.

These results refine our claim: PASTE does **not** preserve an unloaded 93.8% coverage number under arbitrary load. Instead, its benefit decreases with residual speculative capacity, wider budgets help only when those candidates can actually be admitted, and saturation safely disables speculation rather than delaying or changing authoritative execution. We will add the full load-by-budget table and separate static Top-k recall from load-dependent realized coverage. The completed Tongyi target/high GPU results remain a separate evidence tier; the Granite portability attempt failed closed in baseline A and produced no A/E latency result.
